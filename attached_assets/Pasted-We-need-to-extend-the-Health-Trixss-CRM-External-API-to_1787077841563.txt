We need to extend the Health Trixss CRM External API to support TAGGING of CRM records.

IMPORTANT:
This task is for the CRM External API only.
DO NOT modify the healthtrixss-crm-mcp project.
The MCP implementation will be performed separately after this API work is complete.

CURRENT EXTERNAL API

The CRM currently exposes external API support for:

- Accounts
- Contacts
- Leads
- Opportunities
- Activities
- Documents

The existing API uses:
- /api/v1/external
- x-api-key authentication
- organization scoping
- crm.read / crm.write
- activities.read / activities.write
- documents.read / documents.write
- strict validation
- audit logging

Review the existing implementation before making changes, including:

- server/external-api-routes.ts
- server/external-patch-config.ts
- docs/openapi.yaml
- API implementation documentation
- database schema
- existing tag/category functionality anywhere in the CRM application

Do not assume a new database schema is required until you determine whether the CRM already has a reusable tag model.

==================================================
OBJECTIVE
==================================================

Expose a clean, secure external API that allows integrations to create/use tags and assign/remove tags from CRM records.

The following entity types must support tags:

- Account
- Contact
- Lead
- Opportunity
- Activity

If the internal CRM already supports tags on additional entity types, document them, but do not unnecessarily expand scope.

Tags must be organization-scoped.

The same tag should be reusable across multiple entities.

Example:

"CEO Attention"

could be attached to:

ACCT-2025-00030
OPP-2026-000123
ACT-2608-00099

without creating three independent tag definitions.

==================================================
2. TAG MANAGEMENT API
==================================================

Implement external API support for tag management.

Preferred API design:

GET /api/v1/external/tags

Returns tags available to the organization.

Support at minimum:
- search
- limit
- offset

POST /api/v1/external/tags

Creates a tag.

Example:

{
  "name": "CEO Attention"
}

Tag names should be normalized appropriately to prevent accidental duplicates.

For example:

"CEO Attention"
"ceo attention"
" CEO Attention "

should not create unintended duplicate tags if the existing CRM tag model treats these as equivalent.

If the CRM already has tag colors, descriptions, or other metadata, expose them where appropriate.

==================================================
3. ENTITY TAG API
==================================================

Implement a consistent API for assigning tags to records.

Preferred pattern:

GET /api/v1/external/{entityType}/{id}/tags

POST /api/v1/external/{entityType}/{id}/tags

DELETE /api/v1/external/{entityType}/{id}/tags/{tagId}

Supported entity routes:

accounts
contacts
leads
opportunities
activities

Example:

POST /api/v1/external/opportunities/OPP-2026-000123/tags

{
  "tagId": "TAG-000123"
}

If appropriate, ALSO support convenient assignment by tag name:

{
  "name": "CEO Attention"
}

If assignment by name is supported, define clearly whether a missing tag:
A. is automatically created, or
B. returns an error.

Prefer predictable/idempotent behavior.

Adding an already-attached tag should NOT create duplicates.

==================================================
4. FILTERING
==================================================

Extend the existing list APIs so records can be filtered by tag.

Examples:

GET /accounts?tag=Strategic
GET /contacts?tag=Decision-Maker
GET /leads?tag=Conference-2026
GET /opportunities?tag=CEO-Attention
GET /activities?tag=Needs-Follow-Up

If IDs are preferable, support:

?tagId=TAG-000123

Ideally support both tag name and tag ID if it can be implemented cleanly.

Filtering MUST occur before pagination so pagination.total reflects the filtered result.

==================================================
5. READ RESPONSES
==================================================

Determine whether tags should be available through expand behavior.

Preferred:

GET /opportunities/:id?expand=tags

and equivalent support for:

accounts
contacts
leads
activities

Return a normalized representation such as:

"tags": [
  {
    "id": "TAG-000123",
    "name": "CEO Attention"
  }
]

If the existing CRM tag model includes color or other useful metadata, include it consistently.

==================================================
6. SECURITY
==================================================

Preserve existing external API security.

Reading tags:
crm.read

Creating tags:
crm.write

Assigning/removing tags:
crm.write

For activities, determine whether activity tag operations should use:
activities.read / activities.write

or crm.read / crm.write.

Use whichever model is most consistent with the existing authorization architecture and DOCUMENT the decision.

Organization isolation is mandatory.

An API key must never:
- see another organization's tags
- assign another organization's tag
- tag another organization's record
- infer the existence of cross-organization records

Follow the existing 404 behavior for cross-org resources.
