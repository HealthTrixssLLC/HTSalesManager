HEALTH TRIXSS CRM EXTERNAL API
TAGGING + CONTROLLED CRM WRITES + INTEGRATION READINESS

============================================================
MISSION
============================================================

Extend and validate the Health Trixss CRM External API to provide a secure,
general-purpose integration interface for:

1. CRM record reads
2. Controlled CRM record writes
3. Activity creation
4. Tag management
5. Optional tag assignment
6. Safe concurrency
7. Idempotent/replay-safe operations where appropriate
8. Organization isolation
9. Auditability
10. Predictable machine-readable errors

IMPORTANT:

This task is ONLY for the Health Trixss CRM application and External API.

DO NOT modify any downstream integration, MCP server, AI assistant,
automation system, or other client application.

The External API must remain CLIENT-AGNOSTIC.

Do not design business logic around any particular:

- AI assistant
- MCP implementation
- automation platform
- CRM agent
- user interface
- integration consumer

The External API should expose secure primitives that ANY properly
authenticated and authorized client can consume.

============================================================
ARCHITECTURAL RESPONSIBILITY
============================================================

The External API is responsible for:

- authentication
- authorization
- organization isolation
- canonical record identity
- validation
- mutable-field allowlists
- concurrency protection
- idempotency where appropriate
- auditability
- predictable errors
- data integrity

The External API is NOT responsible for:

- conversational approval
- interpreting natural-language intent
- deciding whether a user intended a particular business action
- orchestrating multi-step workflows
- deciding whether a missing tag should be created
- AI-specific behavior
- client-specific business rules

Clients may compose multiple API operations into workflows, but each API
operation must remain explicit, predictable and independently auditable.

============================================================
CRITICAL REQUIREMENT — TAGS ARE OPTIONAL
============================================================

Tags are OPTIONAL metadata.

Tags MUST NOT be required to:

- create an Account
- update an Account
- create a Contact
- update a Contact
- create a Lead
- update a Lead
- create an Opportunity
- update an Opportunity
- create an Activity
- update an Activity
- perform any other normal CRM transaction

Existing CRM operations must continue functioning WITHOUT tags.

There are three independent classes of operations:

1. CRM RECORD OPERATIONS
2. TAG TAXONOMY OPERATIONS
3. OPTIONAL TAG ASSIGNMENT OPERATIONS

A normal CRM create/update operation must not create, assign, remove,
require or otherwise modify tags unless a separate explicit tag operation
is called.

Backward compatibility is mandatory.

PHASE 16 — ATOMIC STALE-WRITE PROTECTION
============================================================

Controlled updates must protect against stale writes.

Example:

1. Client reads record.
2. Another user/system modifies record.
3. Original client submits update based on stale state.
4. API must prevent unintended overwrite.

Implement atomic concurrency protection.

Preferred standard:

ETag + If-Match

Example:

GET /opportunities/OPP-123

returns:

ETag: "abc123"

PATCH /opportunities/OPP-123

If-Match: "abc123"

If the underlying record changed, reject the update atomically.

Use:

412 Precondition Failed

or:

409 Conflict

depending on the most appropriate existing architecture.

Provide a machine-readable code such as:

STALE_RECORD
VERSION_CONFLICT
PRECONDITION_FAILED

The version check and write MUST be atomic.

A client-side:

GET
compare
PATCH

is NOT sufficient.
